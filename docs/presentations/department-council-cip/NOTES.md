# Department Council presentation — source notes

Deliverable: `CIP_Department_Council_Presentation.pptx` (16:9, 12 slides, fully editable).
Generated by `build_deck.js` (pptxgenjs). Re-run with `node build_deck.js` from this folder.

## Typography rule

**No text in this deck is smaller than 14pt.** The type scale lives in the `T` object at the
top of `build_deck.js` (`T.min = 14`), and captions, status badges, footers and slide numbers
all sit on that floor rather than below it. Keep it that way when editing: the deck is sized
for a council room, so shorten copy or enlarge the container rather than dropping a point size.

## Audience and framing

Department Council, faculty, and program leadership. CIP is presented as a Curriculum
Committee software asset that supports curriculum **visibility, review, alignment,
documentation and continuous improvement**. It is explicitly *not* presented as a
replacement for official accreditation or assessment systems.

Scope: **Undergraduate Electrical Engineering only.** MSc/graduate modules exist in the
codebase but are referenced once, as "under construction / pending approval".

The capabilities named on slide 7 are all features that exist in the portal today:
program structure and prerequisite flow, the Course–SO–PI performance heatmaps with their
`Export PNG` action (`undergraduate-ee/program-overview.html`), the textbooks and references
register and its BibTeX-based modification requests (`assets/reference-management.js`), the
teaching strategies and assessment methods page, the CLO review and SO mapping review flows
(`assets/clo-review.js`, `assets/so-mapping-review.js`), the CLO–SO–PI alignment analysis,
NCAAA course specification generation from `templates/EE-CS-NCAAA-Template.docx`
(`assets/ncaaa-cs-generator.js`), CLO revision reports
(`assets/clo-revision-docx-generator.js`), and the jsPDF-based course, review and
change-request PDFs.

Release-integrity wording on the security slides follows `docs/desktop-release-packaging.md`:
each release has an identifier (`r` + 12 digits), a manifest with a lowercase SHA-256 per
file, and byte-reproducible archives. Statements about the desktop application itself
(1.0.0 prepared, PSU email + OTP, OS credential store, private object storage, trusted-user
test) were supplied by the Curriculum Committee — they are not derivable from this repo,
which holds the portal content and the release packager only.

## Screenshots

`screenshots/` holds real captures of the current portal, not placeholders. They were taken
headless at 1600 px wide against a local read-only static server of this repository
(`python -m http.server`), then cropped to the region used on each slide.

`pi-heatmap-crop.png` needed one extra step: the heatmaps sit behind a `Show Heatmaps` toggle,
so that capture was taken by driving headless Chrome over the DevTools protocol (navigate,
click `#toggleHeatmapBtn`, then `Page.captureScreenshot` clipped to the rendered table).

Four are placed in the deck; the rest are kept as alternates for whoever edits it next.

Each placed image is sized to its own pixel aspect ratio, so replacing one with a fresh
capture of the same crop needs no reflow. The crop boxes are recorded in the build history
of `build_deck.js` comments next to each `addImage` call.

To refresh them: serve the repository root statically, then re-run the headless capture and
the crop step. No portal code is modified by any of this.

## Language guardrails observed

- GitHub Pages is described as *public static hosting that did not match our data-governance
  requirement* — never as "insecure".
- No DRM claim, and no claim that an authorized user cannot inspect local files. The stated
  objective is "controlled access, controlled distribution, reduced public exposure, release
  integrity, and managed synchronization of authorized local copies."
- macOS is stated as *not yet built*: "Windows is the first validated desktop platform."
- CIP "supports" review and documentation; it does not replace accreditation systems.
